# Evalia: project rules

Evalia is an independent bid-scrutiny tool for construction owners and lenders. It produces evidence-cited scrutiny reports on construction bids. It does not award contracts. It was inspired by JTC Corporation's EVA, but it shares no code with EVA.

**Current phase:** design. No product code is written until Victor approves [`docs/04-v1-scope.md`](docs/04-v1-scope.md). Version one is limited to producing three scrutiny reports for the discovery test.

## 1. Writing style

All prose follows Financial Times house style (Colin Inman, *The Financial Times Style Guide*). This covers documentation, reports, code comments, commit messages and pull request descriptions.

- **No contractions.** Write "do not", "it is", "cannot", "will not". Quotations are exempt.
- British spelling, with -ise endings: organise, recognise, programme (for a schedule), licence (noun), defence.
- Clear, concise, active voice. No filler words ("actually", "basically", "really", "sort of"). Qualify a claim only when the uncertainty is real.
- Sceptical of unsupported claims, including our own. State the evidence or the reasoning.
- Numbers: one to nine in words, 10 and above in figures. Figures for measurements, money and percentages.
- Money: S$10m, $5bn, €250,000, £3.2m. Write "per cent" in running prose; use "%" in tables and figures.
- Dates: 29 October 2026. Do not write 29/10/2026 or October 29, 2026.
- Headings in sentence case.
- For anything not covered here, follow the FT Style Guide.

## 2. Fact, interpretation and speculation labels

Substantive claims in documents, reports and pull request descriptions carry one of three labels:

- **Fact.** Verifiable from a cited document, a test result or a deterministic computation. Cite the source, page, test or command.
- **Interpretation.** A judgement drawn from facts. Say what it rests on.
- **Speculation.** A hypothesis not yet supported. Say what would test it.

Rules:

- Never present an interpretation as a fact.
- Model output is never a Fact in itself. A quote verified against the source page establishes that the document says something (Fact). What that means for compliance, price or risk is an Interpretation.
- In Evalia reports, every finding has a `basis` field set to Fact or Interpretation. The report shows it.
- Do not claim that code works unless it has been run. State the command and the result.

## 3. Confidential data: tender data never enters the repository

**Never commit tender data.** Tender data means any of the following:

- tender or bid documents, priced BQs, programmes, drawings, correspondence;
- text, tables or images extracted from them;
- model prompts or responses that contain them;
- review workbooks, reports and run records for real engagements;
- names of bidders, projects or clients from real engagements.

All confidential data lives outside the repository, in Victor's OneDrive folder:

```
C:\Users\Victor\OneDrive\Evalia-data
```

- Code finds the folder through the environment variable `EVALIA_DATA_DIR`. Never hard-code the path in code, configuration or tests.
- Tests and examples use synthetic fixtures only (`tests/fixtures/synthetic/`), generated by script and visibly fictitious. Never use a realistic-looking invented record without marking it as fictional.
- Before every commit, run `git status` and `git diff --cached --stat`. Confirm that nothing from the data folder, and no PDF, spreadsheet or Word file from an engagement, is staged. `.gitignore` blocks the common cases, but it is not a substitute for checking.
- If tender data is committed: stop, do not push, and tell Victor. If it has been pushed, treat it as an incident and tell Victor at once. Do not rewrite history without his approval.
- **AI assistants, including Claude Code, are model providers.** Do not read, open, search or summarise anything in `EVALIA_DATA_DIR` unless Victor has explicitly authorised it for that engagement and that engagement's residency policy permits the provider. Cloud coding sessions cannot reach the OneDrive folder, and data must not be uploaded or pasted into them.

## 4. Architecture rules

- **The engine is industry-neutral.** No construction vocabulary (BQ, liquidated damages, PSSCOC and so on) in engine code. Construction knowledge belongs in `packs/construction/`.
- **Packs depend on the engine; the engine never imports a pack.**
- **All model calls go through the LLM gateway.** No vendor SDK is imported anywhere else. No model name is hard-coded outside profile configuration.
- **The residency policy fails closed.** If no permitted profile exists, the call is refused. It never falls back silently.
- **Deterministic checks for arithmetic, presence, dates, thresholds and set differences.** Never ask a model to do arithmetic that code can do.
- **Every finding is traceable** to a document, a page and, where text is relied on, a verified verbatim quote.
- **No finding reaches a report without human review** (accepted or amended).
- **Prompts are pack files** rendered with Jinja2 using strict undefined variables, never `str.format()`.

## 5. Using the DeepSeek material

- `docs/deepseek-source.md` and `extracted/` are reference material, not a codebase.
- Do not copy fragments into product code. Re-derive the logic, write tests first, and check the known defects listed in `extracted/INVENTORY.md`.
- Before relying on any third-party API, verify it against the installed package or its source. The transcript invented APIs for Docling, FROST and Rekor.
- Its integrity apparatus (sealing, ledgers, HSM ceremonies, anchoring, award engine) is out of scope. It must not be reintroduced without Victor's approval.

## 6. Scope discipline

- `docs/04-v1-scope.md` is authoritative once approved. Propose scope changes; do not make them unilaterally.
- Before designing anything new, confirm who the user is, what they need and what is out of scope. Ask when the request is ambiguous.
- Prefer the smallest change that meets the requirement.

## 7. Working practice

- Work on a branch and open a pull request for Victor's review. Never push to `main` directly.
- Commit messages and pull request descriptions follow section 1 and use the labels in section 2.
- Commands for building and testing will be listed here once code exists.
